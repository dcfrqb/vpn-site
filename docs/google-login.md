# Вход через Google

Google Identity Services добавляет вход и регистрацию без пароля сайта. Достаточно личного Google-аккаунта владельца. Google Workspace не нужен.

## Настройки владельца в Google

1. Открой [Google Cloud Console](https://console.cloud.google.com/) под своим Google-аккаунтом и создай проект `CRS VPN`.
2. В **Google Auth Platform → Branding** укажи название `CRS VPN`, свой email поддержки и контактный email разработчика. Для первого теста можно обойтись без логотипа.
3. В **Audience** выбери **External**. В режиме **Testing** добавь свой Google-аккаунт в **Test users**. Internal подходит для пользователей одной организации Workspace, для нашего сайта нужен External.
4. В **Clients → Create client** выбери **Web application**, название `CRS VPN Web`.
5. В **Authorized JavaScript origins** добавь `https://vpn.crs-projects.com`, без пути и завершающего слеша.
6. **Authorized redirect URIs** оставь пустым: сайт получает результат через JavaScript callback.
7. Скопируй **Client ID**, заканчивающийся на `.apps.googleusercontent.com`, и передай его для настройки сайта. Client Secret для этого способа входа не используется. Пароль Google, коды входа и платежная карта не нужны.

Доступ к Gmail и Drive не запрашиваем. Для первого теста достаточно базового профиля входа, дополнительные разрешения API не подключаем.

Перед открытым запуском нужно перевести приложение в Production, проверить требования Google к брендингу и подтверждению домена. Главная страница и политика конфиденциальности, указанные в Branding, должны быть доступны посетителям и Google без общего пароля стенда. Не указывать несуществующие `/privacy` или `/terms`: таких страниц в текущем приложении нет. Добавление политики сайта и снятие общей защиты не входят в эту доработку. Если Google запросит проверку бренда, ее срок зависит от Google.

## Подключение на сервере

В приватном `/opt/vpn-site/.env` задать:

```dotenv
GOOGLE_CLIENT_ID=полученный-client-id.apps.googleusercontent.com
```

Compose передает значение в API. Потребуется пересоздать контейнер API установленным способом деплоя. При пустом значении Google не отображается в форме входа и настройках; API возвращает 503 при попытке начать вход. Значение проверяется во время работы API, пересборка фронтенда для замены Client ID не нужна.

Перед выкатом проверить свободное место и штатные проверки из `deploy/README.md`. Миграция `0003_google_login` добавляет отдельные таблицы идентификаторов Google и одноразовых запросов входа, существующие аккаунты не меняет.

## Поведение

- Новый пользователь получает аккаунт сайта и обычный сеанс в защищенной HttpOnly cookie.
- Повторный вход ищет аккаунт по стабильному Google `sub`, а не email.
- Если email уже занят аккаунтом сайта, автоматического объединения нет. Нужно войти прежним способом и в настройках привязать Google. Это сохраняет аккаунт с его подписками.
- Один Google можно привязать к одному аккаунту сайта. В настройках можно отвязать Google, если остается другой способ входа.
- Новый Gmail считается подтвержденным. Для адреса стороннего почтового провайдера Google не гарантирует текущее владение адресом, поэтому такой email автоматически подтвержденным не отмечается.
- Покупка и выдача VPN без Telegram остаются отдельной задачей.

## Проверки

Локально прошли 112 тестов API с отдельным Postgres, TypeScript и production build. Проверены подпись JWT, неверная подпись, audience, issuer, срок действия, nonce, повторное использование, привязка запроса к сеансу, конфликты email и запрет удаления последнего способа входа.

В Safari проверена форма на ширине 390 и 1280 CSS-пикселей с тестовым Client ID: кнопка Google отображается, горизонтального переполнения нет. Настоящий вход, выдачу Google-токена и работу на опубликованном домене нужно проверить после настройки владельцем настоящего Client ID. Тестовый Client ID не является работающим подключением Google.
